# ADR: Linux local-file attempt history

Status: implemented for independent review, supplementing the process-local ADR. No task acceptance, trust provider, execution permission, operation intent or production hosted service is implied.

Task3.4 can progress without choosing a database/server. `evidence::durable::DurableHistory` is a separate opt-in Linux API; existing LocalHistory remains unchanged and still rejects StorageRequirement::Durable. Caller explicitly creates a new empty owner-private directory or opens an existing initialized directory. Creation never resets nonempty storage. Root/file final symlinks, shared permissions, foreign ownership and multiply linked regular files are rejected. File operations anchor to the opened directory using Linux `/proc/self/fd`; lock/state opens use O_NOFOLLOW/O_NONBLOCK. The controller must control directory ancestry and exclude hostile same-UID mutation, lock deletion, cloned storage and manual snapshot rollback. This is not a multi-tenant security boundary.

Supported filesystem type allowlist: ext-family (ext4 magic), XFS, Btrfs and overlayfs. tmpfs, known network filesystems and unknown types reject. Only Linux overlayfs was exercised in this environment; ext/XFS/Btrfs deployment qualification and real power-loss/storage-controller fault testing are not claimed. Overlay durability is conditional on its underlying host storage honoring file/directory sync; nested remote or volatile backing cannot be inferred from its type. Callers must ensure persistent local backing. Hardware loss, host rollback, filesystem corruption and adversarial owner changes are outside this profile.

A stable `history.lock` file provides nonblocking flock exclusion for every read/transition across processes. Contention returns an explicit retry error without mutation. This is advisory locking among participating processes; external modifications are unsupported. State is one strict versioned `gitguard.local-history/v1alpha1` JSON snapshot containing an append-only logical event sequence and checksum. All events replay through actual GuardEngine InMemoryAttemptStore validation, never a separately invented CAS algorithm. Snapshot rewriting does not remove or rewrite historical events.

Each successful mutation acquires the lock, loads/replays current disk state, validates a native transition, appends its event, writes a same-directory random temporary file, syncs the file, atomically renames it over state.json, then syncs the directory. The API returns success only after both syncs. Single events are capped at64KiB, state at16MiB and10,000events; capacity refuses without compacting/deleting history. The JSON checksum detects accidental corruption and is not authentication. Unknown versions, malformed/checksum-invalid/invalid-transition state, unsafe files and missing initialized state fail closed; no empty fallback exists.

A crash before rename leaves old committed state; a crash after rename can leave new committed state. Failure at/after publication returns an outcome-uncertain error: reopen and inspect/resume the existing run rather than assuming failure and minting another operation. Test-only subprocess exits inject crashes immediately before/after rename; lock release and whole-state replay are checked. These are process-crash tests, not physical power-cut proof. Abandoned staging files are not automatically cleaned or treated as results.

DurableTicket is bound to store identity, full ReuseKey, run and generation. `resume` reconstructs only an exact persisted registration after restart. Completion requires a `consume_bound` result with its privately frozen entire key, including dependency/configuration inputs. Unbound consumption and changed-key relabeling reject. Fresh eligibility/provider evaluation is still mandatory for current authorization; `current/history` are archival snapshots only. Retry/new-run generation advancement clears prior current; stale completion may append but cannot publish over newer generation. Same run ID cannot register twice.

This store persists attempt registration/completion/publication only. It is not task4.4's operation request/intent/receipt state machine, does not atomically persist the separate audit log, does not provide network-wide uniqueness, and enables no writes to repositories or remote platforms. The public methods cannot ingest a caller-supplied eligible boolean; results come from private Consumption. Authority remains supplied by the external controller and defaults unavailable.
