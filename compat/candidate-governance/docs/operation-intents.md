# Durable operation intents

The task 4.4 intent store is an opt-in Linux local storage library, not a grant issuer. The separately authorized local executor consumes its reservation, and the explicit task 4.5 reftable receipt profile is described below. Execution remains disabled by default; production trust-provider selection remains separate.

`IntentStore::create/open` accepts an existing owner-private directory on the same filesystem profile as durable evidence history (Linux ext-family, XFS, Btrfs or overlayfs). Only this environment's overlayfs process crashes/restarts have been exercised; a filesystem type number does not prove hardware power-loss guarantees. Network/pseudo/unknown filesystems reject. The controller must protect the directory and its ancestors against deletion, rollback, copying and same-UID edits. All participating executors must use one store namespace. Copies, hostile filesystem replacement, malicious privileged actors and network-wide uniqueness are outside this local profile.

`prepare(&GrantExpectation)` uses the privately frozen expectation's operation ID and full digest. Its identity includes exact actor/action/repository/candidate/full candidate binding/target/expected target/controller policy. Same ID and digest returns existing historical state; a different digest rejects. Preparing desired work is not authorization. The schema filename `operation-receipt.schema.json` follows the roadmap, but its versioned payload is an **intent observation**, not a hosted platform receipt. The internal Applied transition added by the local executor acknowledges only that its exact local operation returned success; it cannot be requested through the public intent API.

States and generations are closed:

| State | Generation | Meaning |
|---|---:|---|
| prepared | 0 | Durable desired request; no attempt reserved |
| attempt_recorded | 1 | One attempt reservation durably recorded; observers must treat its external outcome as unknown |
| recovery_required | 2 | The reservation holder explicitly reports uncertainty; no replay permitted |

`claim(&prepared_receipt)` is a state CAS. Only the first caller can receive the private, non-Clone/non-Deserialize `AttemptReservation`, and only after file and directory sync. A replay returns an error, never another reservation. The reservation is storage ownership, **not authority to mutate Git**; a future protected writer must revalidate current grant and evidence and execute an atomic platform precondition. `mark_uncertain` consumes a reservation and records the next state. A crash may leave `attempt_recorded` without that marker: this is already non-retryable, not a lease that expires. No API resumes a reservation, resets a state, purges uniqueness history, records a fabricated platform success, or performs compensation. The local executor may append Applied after actual success; local reconciliation matches the full platform-bound request digest and never infers outcomes from current refs. In the default files-backend profile an attempt without that acknowledgement remains unknown. The explicit local reftable profile below additionally checks a platform-side receipt; hosted platform receipt/history integration is still absent. No currently exposed state permits blind retry.

A stable nonblocking `flock` serializes read/modify/commit across participating processes. Every operation reopens the lock without symlink traversal and checks identity and inode against the opened store. The directory descriptor anchors all children. Files must be owner-private regular files with one link. Missing, malformed, unsupported or checksum-inconsistent snapshots never initialize implicitly. Event replay also validates every transition, preventing a rehashed invalid state machine. SHA256 detects corruption, not malicious controller authentication or rollback.

The append-only logical journal is stored by atomically replacing a complete strict snapshot. Temporary file contents are synced before rename and directory sync follows rename. A failure whose commit may have occurred returns `OutcomeUncertain`, no reservation; reopen and observe. The pre-rename process-crash test can leave an uncommitted staging file; it neither resets nor consumes an operation key. A failure after durable commit but before delivery sacrifices availability rather than issue another attempt. No exact-once external mutation claim is made.

Limits: 16 MiB snapshot, 4096 operation IDs, 12288 events, 128-byte IDs and fixed 71-byte digests. A typed event therefore remains below 4 KiB. Borrowed serialization is counted before snapshot/checksum allocation. Input file metadata is checked before bounded read and strict decoding. Capacity exhaustion fails before commit, while existing same-request observations remain readable. Static typed errors contain no caller/provider text. There is no retention deletion because forgetting an operation ID would undermine idempotency.

Tests use actual Git candidate binding without changing its files, private local stores, two independent processes, true process exits before/after atomic replacement, rehashed malformed history, foreign/stale receipts, lock contention/replacement, unsafe paths and quota rejection. Fixture trust labels do not select a production issuer. Schema validation describes data shape only.

## Explicit local reftable receipt profile (task 4.5 slice)

`ProtectedBareTarget::open_reftable_receipts` explicitly selects Linux x86_64, Git **2.47.3 or newer**, SHA-1 and `extensions.refStorage=reftable`. The minimum is the previously validated receipt baseline, not a claim about the earliest upstream reftable release or a global minimum for GitGuard. Numeric release cores with bounded dot-separated alphanumeric distribution qualifiers are accepted; malformed/below-minimum reports, hyphen-qualified release cores and recognized `rc`-prefixed qualifiers refuse this optional profile. Qualifier parsing does not establish the release semantics of every vendor suffix. There is no exact-version lock or upper-version allowlist.

A newer version string alone is insufficient. Before opening the receipt capability, the same restricted runner probes a separate owner-private disposable bare repository: explicit SHA-1/reftable initialization and format readback, blob write/readback, a two-ref prepare/commit transaction, stale-CAS rejection with neither partial update nor new receipt, and prepared abort with both refs unchanged. The complete production probe shares the runner's ten-second deadline; each command keeps the existing process, no-helper, no-network and output limits. Fixed probe/reflog attribution avoids automatic hostname lookup and is not an identity or grant. No probe command operates on the selected target, no caller repository is migrated, and no network or helper permission is added.

The actual selected target retains its original private-directory, config allowlist, physical identity, exact SHA-1/reftable and authorization checks. Ordinary `open` still rejects reftable and does not invoke this optional minimum-version/capability gate; missing receipt support therefore does not disable generic files-backend behavior. The receipt entry still rejects files/unknown backends, extra config and SHA-256. The adapter uses Git plumbing, not binary table parsing. Reftable internals remain [an upstream implementation detail](https://git-scm.com/docs/git-init/2.47.0#Documentation/git-init.txt---ref-formatltformatgt); capability probes and the real crash/recovery suite provide the stated local evidence, not a claim about every future implementation or power-loss behavior. The controller must protect this target and its receipt namespace against edits, copies and rollback, just as it protects the existing intent store.

After the unchanged frozen candidate, action, target, current grant and one-attempt reservation checks, the adapter creates a bounded receipt blob binding the physical target identity, operation ID, full expectation digest, platform request digest and candidate OID. A single fixed `update-ref --stdin` transaction compares-and-swaps the target ref and creates `refs/gitguard/receipts/<operation-ID-hash>`. Both updates share one reftable publication. The crate-generated input is bounded and supplied through a private temporary file; the existing child process, no-helper and no-network restrictions remain unchanged. Fixed `user.name`/`user.email` arguments supply only Git reflog attribution, avoiding automatic hostname discovery; they never replace grant authentication.

Read-only `reconcile` may resolve an already claimed/uncertain intent to historical Applied using that exact platform receipt even after the target advances and the controller acknowledgement is lost. It leaves the controller journal bytes unchanged. Wrong operation/request/platform/candidate, a non-blob, malformed or absent receipt cannot establish completion. Unknown remains unknown; absence is never proof of no write, and there is no recovery retry, compensation or fresh write permission. A stale target prevents both transaction refs from being published; an unreferenced prepared blob is not a receipt.

This specifically avoids a measured files-backend counterexample: after `prepare`, failure committing the second ref can leave the receipt ref updated but the target unchanged. Git 2.47.3's [files transaction implementation](https://github.com/git/git/blob/v2.47.3/refs/files-backend.c) commits separate ref locks. Its [reftable transaction implementation](https://github.com/git/git/blob/v2.47.3/refs/reftable-backend.c) writes the updates in one table; [stack publication](https://github.com/git/git/blob/v2.47.3/reftable/stack.c) publishes the table list through a lock-file rename. The local profile covers process-crash consistency, not power-loss durability, hosted remote receipts, malicious same-UID writers or cross-worktree transactions.

Focused evidence: real SIGKILL after CAS and before controller acknowledgement, then independent reopening and subsequent target advancement; journal preservation; wrong-bound/missing/corrupt receipts stay RecoveryRequired; stale target publishes neither ref; files/default/unknown/extra configuration rejection. The earlier files-backend crash matrix remains applicable without being reinterpreted as platform receipt proof. See ledger `gitguard-receipt-{red,green,files-regression,regression,clippy}.log` and `gitguard-receipt-files-atomicity-probe.json`. Original task 4.5 is independently accepted at `13fd699fc405d108a3f2aeede2797fec1f980824` for this local profile, combined with the prior crash/cancel/retry evidence. See ledger `gitguard-receipt-independent-review.md` and `gitguard-receipt-independent-verification.json`; hosted receipts remain outside this acceptance.
