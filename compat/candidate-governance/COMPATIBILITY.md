# Preserved candidate-governance implementation

This directory preserves the complete tree from GitGuard branch `origin/impl/guard-roadmap-20261009`, commit **`6be082a4b1ae91fce1075ba4fadcb7c17bbc21bc`**. Source, tests, examples, fixtures, schemas, documentation, original README files and the historical workflow remain together. It is a separate compatibility package, not the installed or default GitGuard CLI. The current repository-root implementation and its XML contract take precedence.

## Build boundary

The compatibility package requires **Linux**, Rust **1.90+**, and the original GuardEngine root API at **`b0e4b445e1a20a9354d55ebb41bbedaf16ec8a74`**. Its `Cargo.toml` points to `../../../guardengine-compat`, a sibling of the enclosing GitGuard checkout. That dependency must be a separate checkout of the exact revision; the current installer dependency is not a substitute. The older root API exposes `guardengine::integration`, including eligibility, attempt-store and evidence-envelope types absent from the newer shared root API.

From the enclosing GitGuard checkout, after preparing the pinned sibling dependency:

```sh
cargo test --locked --manifest-path compat/candidate-governance/Cargo.toml
cargo clippy --locked --manifest-path compat/candidate-governance/Cargo.toml --features privileged-execution --lib --test runner_security --test atomic_admission --test executor_disabled --example local_bare_apply -- -D warnings
```

These are verification instructions, not claims that every target has passed. The package has Unix-specific filesystem/process code, fixed `/usr/bin/git` and `/dev/null` paths, and a restricted Linux process profile. Windows/macOS compatibility is not implied by the current root CLI's platform support. Build outputs and command invocation are separate from the current root package; do not install this historical binary over the current `gitguard` executable.

## Policy and execution boundaries

The current runtime authority remains `<git-common-dir>/gitflow.xml` through the current shared policy loader. The preserved `adapters/gitflow` code and JSON captures are an explicitly opt-in historical observation profile. They must not supply current runtime policy, a JSON fallback, CI authorization or a replacement for the latest XML gate. Legacy generic evidence contracts and request JSON are their original compatibility interfaces, not additional GitFlow policy authorities.

Privileged writes remain **off by default**: Cargo's default feature set is empty, `ExecutionConfig.enabled` defaults false, and the actual local apply functions require both `privileged-execution` and enabled configuration plus their original authorization/state checks. The generic operation entrypoint still refuses authorization. Retaining this source does not enable mutation transports, credentials, remote push, host trust or production enforcement. Privileged fixture examples must only be run under separately authorized, isolated acceptance procedures.

The archived `.github/workflows/` under this directory is historical source; GitHub does not execute nested workflow directories. Any current compatibility CI must explicitly select this manifest, fixed dependency and Linux profile. Fixture provenance, captured output, script source pins and source-bundle hashes remain historical evidence, not refreshed results.

## Optional receipt minimum and capability checks

The current compatibility receipt API supports Git 2.47.3 and newer only when the required capabilities pass an independent private-repository probe. The previously validated 2.47.3 baseline becomes a minimum, not an exact pin, and is not imposed on generic GitGuard/files-backend behavior. Version reports accept numeric release cores and bounded dot-separated alphanumeric distribution suffixes; malformed/below-minimum cores, hyphen-qualified cores and recognized `rc`-prefixed qualifiers are rejected. Unknown vendor qualifier semantics are not inferred. A new enough version without reftable/transaction support still refuses the optional receipt capability.

The probe uses the same restricted Git runner and a ten-second cumulative deadline. It checks explicit SHA-1/reftable plumbing, two-ref prepare/commit and readback, stale-CAS all-or-none rejection, prepared-abort preservation and blob readback in its own temporary repository. It never writes to the selected target, parses binary reftable internals, enables helpers/network, or changes target permission/configuration/identity/authorization checks. See [the updated receipt contract](docs/operation-intents.md#explicit-local-reftable-receipt-profile-task-45-slice). Historical README and recorded evidence retain their original exact-version descriptions; this current contract supersedes that version restriction. The matrix retains 2.47.3 and exercises the current Git release separately.

A sixth fixture file, `tests/cli_outcomes.rs`, prepares serialized request bytes in a private temporary regular file, rewinds it, and supplies it as child stdin instead of racing a parent pipe writer against early CLI argument rejection. The original `examples/local_bare_apply.rs` additionally replaces its unbounded two-party barrier with a bounded fixture rendezvous. The new helper `examples/support/local_bare_rendezvous.rs` and three tests in `tests/local_bare_rendezvous.rs` exercise missing-peer, early-return and successful two-party behavior. The original `tests/atomic_admission.rs` and `tests/worktree_creation.rs` now reuse that same bounded helper for three conditional authority-callback rendezvous: the two atomic CAS tests synchronize on the second authority callback, while independent worktree publication synchronizes on its third callback after prepared staging. Each returned worker result notifies its peer; both join outcomes, callback counts and gate state are printed before assertions. Existing winner, durable-intent, target-OID, reconcile and retained-unknown-staging assertions remain. The unconditional first-action barrier in `tests/result_races.rs` is unchanged. These are additional explicit fixture preservation exceptions, not production behavior changes.

## Concurrent scratch-index correction

`src/git/repository.rs` and `src/subject.rs` are additional explicit production-code preservation exceptions. One shared `Repository` owns one private scratch index; concurrent candidate observations formerly copied into that same file without exclusion before `ls-files` read it. A deterministic after-copy/before-read scheduling regression demonstrated overlapping observations, and eight threads performing 32 real candidate validations each reproduced `GitFailed` errors on an unchanged tracked source. Apply maps those validation failures to `Binding` before its first authority callback, matching the newly visible bounded CI diagnostic. This establishes a real shared-scratch race; it does not attribute every historical failure to the same cause.

The minimal repair adds a per-Repository mutex spanning the entire scratch-index metadata check, copy, Git read and manifest parsing. The repository is not Clone; its sole constructor initializes the mutex. No other operation writes or reads that shared index outside this path. Target-worktree preparation uses a different unpublished Git directory. Poisoned ownership returns `UnsafeStorage` rather than recovering or asserting cleanliness. Source index/worktree bytes remain unchanged, and existing file-type/size, digest, cleanliness, candidate-binding and authorization checks are retained. This serialization is not protection against external concurrent edits to user files or hostile same-user mutation.

The three regressions cover deterministic observation exclusion, 256 real concurrent candidate validations without false failure or source writes, and fail-closed poisoning. All 30 requested competing CAS/worktree executions also pass without discarding failed iterations. Earlier RED evidence retains both real failures before the mutex; later verification is recorded separately.

After the scratch-index serialization fix, local Git 2.47.3 full suites under umask 022 passed **157 default tests** and **174 privileged-execution tests**, each retaining one existing ignored external-binary test. All three new scratch-index regressions, all 30 requested competing operations, the original six-case example and required/affected Clippy targets passed. The example recorded two authority callbacks per competing worker and two successful arrivals, one acknowledged CAS plus one RecoveryRequired result, and an unchanged source digest. Same-revision minimum/current Git CI remains the final acceptance requirement.
